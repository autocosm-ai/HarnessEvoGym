执行摘要

HarnessEvoGym 当前定位：可信、可复现的 Agent Harness 递归自我改进（RSI）研究预览版。已实现核心 Controller、五种 Population Mode、OmegaUse-OfficeVal 和 HLE Text-only Math 双环境验证、Mutation Catalog、SearchStrategy 可插拔协议、Server API 与 Core Engine 分离。

商业化核心结论：优先 To B，阶段性探索 To C。

为什么优先 To B：
  • 价值可量化：企业 Agent 项目有明确 KPI（任务成功率、处理时长、成本），改进 5-10% 即有显著 ROI
  • 付费意愿强：企业为节省调优人力和缩短上线时间愿意付费，决策周期可控
  • 环境可控：企业私有部署或托管服务能接入真实评测环境、代码库、业务数据，不需要从零构造 Benchmark
  • 信任要求高：企业接受"控制平面可信、Candidate 隔离、Sealed Final 不可重复打开"等设计，个人用户对审计链和隔离的理解成本高
  • 反馈快：企业客户会明确提出缺失能力和集成需求，指导产品迭代
To C 场景保留但不优先：
  • 适合场景：开发者个人优化自己的 Agent、研究者复现论文、教育场景学习 RSI
  • 挑战：个人用户缺乏真实评测环境、很难构造可靠 Benchmark、付费意愿低、支持成本高
  • 策略：保持开源 Core Engine、提供详尽文档和示例，通过社区驱动；待 To B 产品成熟后，可提供 SaaS 形式的托管优化服务（Freemium 模式）
绝对不要一开始做的事情：
  • ❌ 在没有真实客户反馈前开发通用 Web 控制台和复杂权限体系
  • ❌ 过早标准化所有 Target/Environment，导致为假设场景写大量适配代码
  • ❌ 把 Updater、SearchStrategy 做成低代码拖拽工具（客户需要的是结果，不是更复杂的配置界面）
  • ❌ 承诺"自动超越人类专家"或"保证提升 X%"（应强调辅助人类、可审计、可回滚）
  • ❌ 直接向 C 端用户承诺 SLA 和 7×24 支持

产品价值衡量指标：

维度 主指标 辅助指标
效果 目标任务成功率提升幅度（validation → sealed final 一致性） Bad Case 覆盖率、泛化到新题的稳定性
成本 单次改进的 Token/算力消耗、人工审核工时节省 Candidate Credit、Provider 请求次数、失败重试成本
时间 从 H0 到可交付 Champion 的墙钟时间 单轮 Updater Session 延迟、Resume 后恢复速度
可靠性 基础设施故障暂停率、sealed final 不可重复打开保证 Provider 重试成功率、Checkpoint 恢复完整性
可审计性 完整 Lineage、Diff Guard 覆盖、Mutation Report 完整性 凭据隔离、日志脱敏、决策可重现

三阶段产品演进

阶段一：开源 Core Engine（HarnessEvoGym）

定位：面向研究者和高级开发者的 RSI Gym / Core Engine，用于复现论文、验证算法、扩展 Target/Environment。

用户画像：

  • Agent 框架开发者（需要对比不同 Population Mode 和 SearchStrategy）
  • 研究机构（发表 RSI、AutoML、Agent 优化论文）
  • 企业 AI 团队技术预研（评估 RSI 可行性）

当前已支持：

  • ✅ 完整 Controller + 五种 Population Mode
  • ✅ OmegaUse-OfficeVal 和 HLE 双环境
  • ✅ Mutation Catalog、Diff Guard、Sealed Final
  • ✅ 可复现实验（固定 Source、Seed、Split、Policy）
  • ✅ 本地 Server API（Run 管理、Resume、Fork）

缺少但需要补齐：

  • ⚠️ 完整文档（quickstart、tutorial、best practices、troubleshooting）
  • ⚠️ 更多真实 Target/Environment 示例（SWE-bench、Harbor、自定义 Harness 模板）
  • ⚠️ 端到端 Smoke 测试纳入 CI
  • ⚠️ 版本策略和发布流程
  • ⚠️ 性能基准和资源消耗参考

开源价值：

  • 建立 RSI 领域信任和声誉
  • 获取社区反馈和贡献（Target、Environment、Strategy 扩展）
  • 为企业产品导流（企业用户从开源版开始试用）

阶段二：APP Server（类似 Coding Agent App Server）

定位：企业级 RSI 后端服务，支撑 CLI、桌面端、Web 控制台，提供 Run 管理、队列、持久化、认证、多租户、可观测性。

核心能力：

模块 当前状态 需要补齐
Run 生命周期 ✅ 创建、查询、Resume、Cancel、Fork ⚠️ 优先级队列、并发控制、过期清理
Worker 与队列 ❌ 当前用子进程 ⚠️ 独立 Worker 池、消息队列（Redis/RabbitMQ）、崩溃恢复
持久化 ❌ 当前用本地文件 ⚠️ PostgreSQL（Run、Candidate、Branch、Event）+ S3/MinIO（Checkpoint、Artifact）
认证与租户 ❌ 无 ⚠️ JWT/OAuth、Tenant 隔离、API Key 管理
可观测性 ✅ 本地事件日志 ⚠️ Metrics（Prometheus）、Tracing（Jaeger）、Alert
费用计量 ✅ Branch 级别 Token 计数 ⚠️ Population 全局预算、按客户计费、成本预测
权限体系 ❌ 无 ⚠️ RBAC（Owner/Editor/Viewer）、Experiment 共享

关键决策：

  • 保持 Core Engine 独立：APP Server 调用 Core Engine CLI，不把 Controller 逻辑搬进 HTTP 层
  • 兼容本地部署：企业私有部署时，Worker 和数据库都在客户内网
  • 支持混合云：控制平面在客户内网，Solver/Updater 可选托管算力或客户自有 GPU

阶段三：商业产品（全栈 RSI 优化平台）

定位：客户接入自己的 Harness、代码库、任务/评测环境、预算和目标，系统自动搜索、验证、交付改进版本。

完整价值链：

  1. 接入：客户提供 Git 仓库（Agent 代码）、Benchmark（任务集或真实业务数据抽样）、评测脚本、目标指标
  2. 配置：系统自动或半自动生成 Target Adapter、Environment Adapter、Mutation Catalog
  3. 基线评测：系统对当前版本（H0）做完整基线评测，确认起点性能
  4. 自动搜索：系统按预算运行 Population，自动选择 SearchStrategy 和 Updater
  5. 人工审核：系统推荐 Champion 候选，客户审核 Diff、Mutation Report、validation 结果
  6. 最终验证：客户确认后，系统在 sealed final 上评测，生成审计报告
  7. 交付：系统输出 Git patch、完整 lineage、性能对比、成本报告

产品形态：

  • 企业私有部署：完整控制平面 + Worker 部署在客户内网，数据不出内网
  • 托管优化服务：客户通过 API 提交任务，平台提供算力和托管 Worker，结果回传
  • 混合模式：控制平面和数据在客户侧，算力按需租用云端 GPU Worker

关键差异化能力：

  • ✅ 可信边界：Controller、Evaluator、Sealed Final 不被 Candidate 修改
  • ✅ 可复现：完整 Source、Seed、Split、Policy、Lineage 固定
  • ✅ 可审计：Diff Guard、Mutation Report、完整事件流
  • ✅ 可回滚：晋升失败自动回退，不污染 Champion
  • ✅ 灵活搜索：五种 Population Mode + 可插拔 Strategy，而非单一黑盒优化

优先 RSI 方向与商业价值

以下方向按当前 HarnessEvoGym 能力匹配度、客户痛点明确性、商业价值排序。

1. Coding Agent Harness 优化
已部分支持 优先级：最高

优化对象：编程 Agent 的 Prompt、Tool、Agent Loop、错误处理、多步规划

客户痛点：

  • 企业自研 Coding Agent 在特定语言/框架上表现不稳定
  • 人工调优 Prompt 和工具链耗时长（数周到数月）
  • 没有系统化方法验证改进是否真正泛化

商业价值：

  • 💰 企业愿意为"任务成功率从 60% 提升到 75%"支付显著费用
  • 💰 缩短上线时间（从人工调优 2 个月到自动优化 1 周）
  • 💰 可复用到多个项目和语言

评测环境：

  • ✅ 已支持：OmegaUse-OfficeVal（91 任务）
  • ⚠️ 需补齐：SWE-bench Verified（真实 GitHub issue）、企业内部代码库任务

技术难点：

  • SWE-bench 环境复杂（需 Docker、多版本依赖、长时间运行）
  • 企业代码库需接入私有 Git、CI/CD、测试框架
  • 评测指标多样（代码正确性、测试覆盖、可维护性）

当前能力匹配：⭐⭐⭐⭐ 4/5（MSA Cowork 已验证核心链路，需补齐 SWE-bench 适配）

2. 知识工作 Agent（Office/文档/数据处理）
已支持 优先级：高

优化对象：文档生成、表格处理、数据清洗、报告自动化的 Agent

客户痛点：

  • 企业内部大量重复性知识工作（财务报表、合规文档、数据整理）
  • 通用 Agent 在企业特定格式/规则上表现差
  • 需要符合企业模板和审批流程

商业价值：

  • 💰 直接节省人力（1 个 Agent 替代 0.5 FTE 重复工作）
  • 💰 市场广阔（几乎所有企业都有知识工作自动化需求）
  • 💰 客户续费率高（一旦接入真实流程，替换成本高）

评测环境：

  • ✅ 已支持：OmegaUse-OfficeVal（Word/Excel/PPT 任务）
  • ⚠️ 需补齐：企业自定义模板、多语言文档、API 集成（Notion/飞书/钉钉）

技术难点：

  • 企业模板和规则难以标准化
  • 评测指标主观性强（文档质量、格式美观度）
  • 需要接入企业内部系统（ERP/CRM/审批流）

当前能力匹配：⭐⭐⭐⭐⭐ 5/5（OfficeVal 已完整验证，直接可商业化）

3. 数学推理 Agent 优化
已支持 优先级：中

优化对象：数学证明、竞赛题求解、形式化验证的 Agent

客户痛点：

  • 教育机构需要自动批改和辅导数学题
  • 研究机构需要自动化定理证明
  • 通用模型在特定数学领域（如数论、拓扑）表现弱

商业价值：

  • 💰 教育市场（K-12、高等教育、竞赛培训）
  • 💰 研究工具（加速形式化验证、定理证明）
  • ⚠️ 付费意愿相对企业场景较低

评测环境：

  • ✅ 已支持：HLE Text-only Math（固定 split、sealed test）
  • ⚠️ 需补齐：更多数学竞赛数据集（AMC、AIME、IMO）、Lean 形式化证明

技术难点：

  • 数学题多样性高，泛化困难
  • 形式化证明需要 Lean/Coq 集成
  • 商业化路径不如 Coding/Office 明确

当前能力匹配：⭐⭐⭐⭐ 4/5（HLE 已验证，但商业场景需进一步探索）

4. 企业流程自动化 Agent
研究方向 优先级：中高

优化对象：RPA、工单处理、客服对话、审批流程的 Agent

客户痛点：

  • 企业有大量结构化流程（审批、工单、客服）
  • 通用 Agent 不理解企业特定术语和规则
  • 需要与企业 ERP/CRM/工单系统集成

商业价值：

  • 💰 市场巨大（RPA 市场规模百亿美元）
  • 💰 客户付费意愿强（直接替代人力）
  • 💰 长期合同（年度订阅或按流程计费）

评测环境：

  • ❌ 当前无标准 Benchmark
  • ⚠️ 需从零构建：模拟企业系统、工单数据、审批规则

技术难点：

  • 企业系统集成复杂（API、权限、数据隐私）
  • 流程规则难以标准化（每个企业不同）
  • 评测需要模拟真实企业环境
  • 竞争激烈（UiPath、Automation Anywhere 等成熟 RPA 厂商）

当前能力匹配：⭐⭐ 2/5（需大量前期工作构建 Environment 和 Benchmark）

5. Agent 评测策略与工具调用优化
研究方向 优先级：中

优化对象：Agent 的工具选择、参数生成、错误处理、重试策略

客户痛点：

  • Agent 频繁调用错误工具或生成无效参数
  • 缺乏系统化方法优化工具调用链
  • 工具调用成本高（每次调用都消耗 Token）

商业价值：

  • 💰 降低 Agent 运行成本（减少无效工具调用）
  • 💰 提升成功率（正确工具 + 正确参数）
  • ⚠️ 更像"特性优化"而非独立产品

评测环境：

  • ✅ 部分支持：MSA Cowork 中包含工具调用
  • ⚠️ 需补齐：专门的工具调用 Benchmark（ToolBench、API-Bank）

技术难点：

  • 工具调用链复杂（多步依赖、状态管理）
  • 评测指标多样（正确性、效率、成本）
  • 商业化路径不明确（更适合作为其他方向的子模块）

当前能力匹配：⭐⭐⭐ 3/5（核心能力具备，但需专门 Benchmark 和客户场景验证）

推荐优先级排序（0-6个月）：
  1. 知识工作 Agent（OfficeVal 路径） — 已验证，直接商业化
  2. Coding Agent + SWE-bench — 客户需求明确，需 3-6 周补齐环境
  3. 数学推理 Agent — 教育市场探索，作为技术展示
  4. 企业流程自动化 — 长期方向，需要客户深度合作共建 Benchmark
  5. 工具调用优化 — 作为其他方向的增强特性，而非独立产品

分阶段路线图

现在（0-3个月）

目标：稳定开源版，完成首个商业化 PoC

必须交付：

  • ✅ 补齐开源文档（Quickstart、Tutorial、API Reference、Troubleshooting）
  • ✅ SWE-bench Verified 环境适配（至少 50 个任务端到端验证）
  • ✅ 端到端 Smoke 测试纳入 CI
  • ✅ 版本策略和发布流程（v0.2.0 稳定版）
  • ✅ 性能基准和资源消耗参考文档
  • ✅ 首个商业 PoC：与 1-2 家企业合作，在真实 Coding Agent 或 Office Agent 场景验证

验收指标：

  • 新用户从 git clone 到运行第一个实验 < 30 分钟
  • SWE-bench 环境稳定性 > 95%（任务执行不因基础设施失败）
  • 至少 1 个企业客户完成 PoC，验证 5-10% 性能提升
  • GitHub Stars > 500，贡献者 > 10

明确不做：

  • ❌ Web 控制台（CLI 和 API 足够 PoC）
  • ❌ 多租户和认证（单客户私有部署）
  • ❌ 复杂计费系统（PoC 阶段按固定价格或免费）
近期（3-6个月）

目标：APP Server 基础能力，开始商业化落地

必须交付：

  • ✅ Worker 与队列系统（Redis + 独立 Worker 进程池）
  • ✅ 持久化层（PostgreSQL + S3/MinIO）
  • ✅ 基础认证与多租户（JWT、Tenant 隔离）
  • ✅ 简化 Web 控制台（Run 列表、状态监控、日志查看、Diff 对比）
  • ✅ 可观测性（Prometheus Metrics、Grafana Dashboard）
  • ✅ 全局费用预算与成本预测
  • ✅ 商业落地：3-5 家付费客户，至少 1 个年度合同

验收指标：

  • 支持 10+ 并发 Run，单 Worker 崩溃不影响其他 Run
  • Run 恢复成功率 > 99%（从 Checkpoint 恢复）
  • Web 控制台覆盖 80% 常用操作（剩余 20% 用 CLI）
  • 客户满意度 > 4/5，至少 1 个客户续约或扩大使用
  • ARR（年度经常性收入）> $50K

明确不做：

  • ❌ 拖拽式配置界面（用 YAML/JSON + 预设模板）
  • ❌ 复杂 RBAC（只支持 Owner/Editor/Viewer）
  • ❌ 公有云 SaaS（先做私有部署和托管服务）
中期（6-12个月）

目标：完整商业产品，扩展到多个 RSI 方向

必须交付：

  • ✅ 自动 Adapter 生成（从客户 Git 仓库半自动生成 Target/Environment）
  • ✅ 混合云支持（控制平面内网 + 算力云端 GPU Worker）
  • ✅ 完整 RBAC 与审计日志
  • ✅ 高级 SearchStrategy（强化学习、贝叶斯优化、遗传算法）
  • ✅ 多 Updater 并行（同时尝试多个修改方向，取最佳）
  • ✅ 统计显著性验证（多 Trial、Bootstrap、置信区间）

架构演进图

架构演进原则：

  • 保持 Core Engine 独立：阶段二和三都复用阶段一的核心逻辑，不重写 Controller
  • 渐进式增强：每个阶段只增加必要的企业级能力，不过度设计
  • 向后兼容：阶段二支持阶段一的 CLI 和本地运行模式；阶段三支持阶段二的 API
  • 灵活部署：客户可选私有部署、托管服务、混合云或公有云 SaaS

关键假设验证

假设 1：企业客户愿意为 5-10% 的 Agent 性能提升付费
  • 验证方法：PoC 阶段明确量化提升幅度，询问客户支付意愿
  • 反例应对：如果客户认为提升幅度不够，探索"按成功付费"或"保证提升 X% 否则退款"
假设 2：自动优化比人工调优更高效
  • 验证方法：对比人工调优 2-4 周 vs 系统自动优化 1 周的时间和成本
  • 反例应对：如果自动优化时间过长或成本过高，优化 SearchStrategy，或提供"混合模式"（系统推荐 + 人工筛选）
假设 3：客户能够提供可靠的评测环境和 Benchmark
  • 验证方法：PoC 阶段评估客户 Benchmark 质量（覆盖率、代表性、可复现性）
  • 反例应对：如果客户 Benchmark 不可靠，提供"Benchmark 咨询服务"或"半自动生成 Benchmark"工具
假设 4：开源 Core Engine 能带来企业客户导流
  • 验证方法：追踪企业客户来源（GitHub → PoC 咨询 → 付费合同）
  • 反例应对：如果开源转化率低，加强技术营销（论文、博客、案例）或直接 BD 头部客户

退出与调整策略

如果商业化不顺利，可考虑：

  • 转型：专注开源项目和学术影响力，不追求短期收入
  • 精简：只做专业服务（咨询、定制开发），不做产品化
  • 合并：被大厂（LLM 平台、Agent 框架）收购或合作集成
  • 开源维护：核心团队转向其他项目，社区接手维护
